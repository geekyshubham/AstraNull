# AstraNull on AWS (`astranull.site`)

Single Ubuntu VM in `us-east-1f`: Postgres + control plane + isolated probe, recovery, and policy workers + Caddy (HTTPS).

A successful same-repository `push` CI run for the current `main` SHA triggers deployment. The workflow checks out that exact SHA; requires `ops/aws/deploy.sh`, `ops/aws/release-state.sh`, and `scripts/postgres-retention-helper.py` to be regular tracked files with no diff from that checkout; hashes all three; transfers them to SHA/run/attempt-bound temporary paths; and verifies all three hashes on the VM before execution. It explicitly sources the transferred state helper and passes the exact private transferred retention helper through the deploy-only environment boundary, so pre-checkout backup pruning never trusts a potentially stale host copy. Local and remote exit/signal cleanup remove all three temporary paths. The VM rejects stale SHAs, dirty checkouts, overlapping deploys, permissive `.env` files, failed encrypted backups, unhealthy workers, and failed internal or public health checks. Secrets live in `ops/aws/.env` on the instance and GitHub Actions secrets—never in git.

## Stack

| Piece | Where |
|---|---|
| VM | EC2 Ubuntu 22.04, Elastic IP |
| App/workers | Image-only services bound to exact local `sha256:` IDs in three groups (control, core/ops, connector); `deploy.sh` builds `ops/aws/Dockerfile` from the exact commit archive |
| DB | Postgres 16 on the same VM |
| DB roles | Short-lived `migrate` uses owner `astranull`; runtime services use `astranull_app` (`NOBYPASSRLS`); one-shot dumps use SELECT-only `astranull_backup` (`BYPASSRLS` is required to read all FORCE-RLS rows) |
| TLS | Caddy → Let's Encrypt for `astranull.site` / `www` |
| Backups | Bounded-stream AES-256-GCM binary-v2 custom dumps; current names are exact, calendar-valid UTC `postgres-YYYY-MM-DDTHH-MM-SS-mmmZ-<12-lowercase-hex>.dump.enc`; manifest-last publication makes a current artifact+manifest pair the only completion marker in `/opt/astranull-backups` (newest 10 current pairs retained); exact calendar-valid pre-nonce legacy names are preserved but excluded from inventory/retention; legacy v1 restore remains supported |

## First boot

1. Clone to `/opt/astranull` and ensure the deploy user owns the clean checkout.
2. Copy `ops/aws/env.example` to `ops/aws/.env`, fill every required core secret/tenant scope, leave connector-only passwords/keys/encryption blank while connectors are disabled, and run `chmod 600 ops/aws/.env`. Do not add the three `ASTRANULL_*_IMAGE_ID` variables; deploy/restore inject them from verified local images. To enable connectors, generate two distinct 64-hex connector database passwords and a third distinct 64-hex connector vault key, generate one matching Ed25519 private-PKCS8/public-SPKI DER base64 keypair, set an explicit connector tenant scope, set `ASTRANULL_WAF_POSTURE_ENABLED=1`, then set `ASTRANULL_CONNECTORS_ENABLED=1` (or a true tenant override) and run the Compose validator before deployment. The validator applies the runtime's strict `1`/`0` boolean rules, requires the control plane, connector scheduler, and connector runner to receive the same WAF flag, rejects enabled connectors while WAF posture is disabled, rejects blank or mismatched connector credentials/keys, and rejects projection of any connector credential while connector mode is disabled. Never copy placeholders or enable before all connector credentials are present.
3. Generate dedicated 64-hex values for `POSTGRES_PASSWORD`, `ASTRANULL_DATABASE_APP_PASSWORD`, `ASTRANULL_DATABASE_BACKUP_PASSWORD`, `ASTRANULL_BACKUP_ENCRYPTION_KEY`, and `ASTRANULL_SECRET_ENCRYPTION_KEY`. All five must be distinct; deployment preflight rejects missing, malformed, mismatched, or reused values before checkout. Enabled connector credentials must also be distinct from these and from one another.
4. Confirm the rendered Compose model gives `backup-dump` only the `astranull_backup` URL, gives `backup` only its encryption key (plus `NODE_ENV`), and gives the profile-gated pinned-PostgreSQL `restore-db` service exactly two owner URLs: one for maintenance database `postgres` and one for target database `astranull`. It must expose no other environment entry, and none of these credentials may reach a long-lived service. The validator enforces these boundaries automatically.
5. Create `/opt/astranull-backups` owned by the deploy user with mode `0700`. The deploy script creates `/opt/astranull-backups/deploy-state` with mode `0700`. Its authority is one mode-`0600` canonical bundle, `release-image-current`; an in-progress activation or rollback is journaled as `release-image-pending`. Each ordered 11-line bundle contains schema `astranull.release-image-bundle`, version `1`, control/core/validator exact 40-character tags plus immutable `sha256:` IDs, and connector enabled intent plus an optional tag+ID. The older `control-plane-image-tag`, `core-worker-image-state`, `connector-image-state`, and `release-validator-image-state` files are regenerated compatibility projections only and must never be edited or treated as authority. All state lives outside the Git checkout.
6. For initial bootstrap only, invoke an exact current-main revision: `bash /opt/astranull/ops/aws/deploy.sh <40-character-sha>`. Subsequent releases use the CI workflow's verified temporary script.

Normal releases must use the CI-triggered GitHub workflow, not a manual Actions bypass. At the start of each deploy or restore, the script rejects an `ops/aws/.env` source that is a symlink, non-regular file, extra hard link, wrong owner, or anything other than mode `0400`/`0600`. It acquires `/opt/astranull-backups/deploy.lock` only after validating the mode-`0700`, deploy-user-owned backup directory; the lock must be a singly linked regular mode-`0600` file, and the opened fd/inode must still match its pathname after `flock`. It copies `.env` exactly once into a private mode-`0600` file in that directory before rendered-model validation. Every subsequent scripted Compose call uses only that immutable environment snapshot; restore also copies the clean checked-out Compose file once into the same private workspace. A live source edit therefore cannot change an operation in progress. Checked cleanup verifies deletion and final absence (including symlinks) on normal, error, and signal paths; startup under the shared lock first removes verified prior-PID one-shot containers, then stale private env/Compose/iid files, then plaintext/backup orphans, so SIGKILL leftovers cannot keep executing or race a new publication. A leak, unsafe hard link, or failed deletion is visible and fails the operation. `deploy.sh` snapshots Compose independently from the target SHA and the previously deployed SHA. Normal backup, migration, and activation phases use only the target-SHA snapshot; the previous snapshot is reserved for explicit or automatic rollback. The AWS Compose file is image-only for the control plane, workers, and one-shot ops services: it contains no `build`, build `context`, or `dockerfile` keys, so `docker compose up` cannot turn the host checkout into a release image. `deploy.sh` is the sole AWS control-plane build path and builds only from `git archive` of the requested exact SHA, never from the orchestration worktree, so ignored or untracked host files cannot enter the release image. Docker writes that archive build's immutable identity through `--iidfile`; the mutable exact-SHA tag must resolve back to that ID but is never itself the identity source.

Each connector decision renders `docker compose config --format json` exactly once from those immutable inputs into a deterministic operation-PID path created exclusively at mode `0600`. The same private render is fed to a full release-image validator with `--print-connector-mode`; only exact `enabled` or `disabled` output is accepted, and every other output or validator error fails closed. There is no success-token or inline-parser fallback. A normal target release validates with the requested immutable image, completes connector and identity compatibility checks, and rebinds it only in the dedicated `astranull-release-validator:<40-sha>` namespace. That validator identity remains part of the intended pending bundle. Explicit rollback and restore require, resolve, and rebind the validator in canonical current state before backup extraction or outage work. Automatic rollback records the validator for the Compose snapshot it actually retains: previous validator for previous Compose, target validator for target Compose. If retained Compose enables connectors but no compatible prior connector identity can run, rollback fails closed instead of publishing a contradictory connector-disabled bundle. The render is never regenerated or printed, and checked cleanup removes it on normal, error, and signal paths.

Every AstraNull Compose application workload executes by a full local image ID, never by a tag: `control-plane` uses `ASTRANULL_CONTROL_PLANE_IMAGE_ID`; core workers plus `migrate`, `backup-role-bootstrap`, and `backup` use `ASTRANULL_CORE_WORKER_IMAGE_ID`; connector scheduler/runner use `ASTRANULL_CONNECTOR_WORKER_IMAGE_ID`. Deploy/restore validate and export these variables internally, and the rendered model requires one exact lowercase `sha256:` ID per group. The validator itself is also executed by raw immutable ID; its dedicated tag exists only for exact-state rebinding. `restore-db` is not an AstraNull application image: it is a profile-gated, digest-pinned PostgreSQL tool. Runtime verification requires both Docker `Config.Image` and `.Image` to equal the expected full ID. Exact-SHA tags and persisted tag fields are audit, compatibility-rebinding, and rollback labels only; they never select an AstraNull image for Compose execution.

On a no-state first boot, the script first builds and validates the requested exact SHA, proves the host has no application/runtime container, no Postgres container, and no Compose `pgdata` volume, then writes the complete pending target bundle **before** starting Postgres, backup, or migration. A SIGKILL after that point can resume only when the pending control/core/validator/connector identities exactly match the requested SHA and raw image ID and every application service remains absent; an existing Postgres container or volume is accepted only through that exact preactivation journal. A volume without either canonical state or the exact first-boot journal, any stopped application runtime, or conflicting state fails closed. Before the encrypted dump, a one-shot target-image bootstrap creates or rotates only the SELECT-only `astranull_backup` role; it neither applies migrations nor starts runtime services. The backup then completes and is verified before the profile-gated migration service applies migrations and atomically creates/rotates `astranull_app` plus `astranull_backup`; both the outer Compose run and the in-container migration command have hard deadlines. Thus existing application data and schema are backed up before any target migration or runtime activation. The app role gets runtime DML with `NOBYPASSRLS`; the backup role has its ACLs reset to SELECT-only and receives `BYPASSRLS` solely because complete dumps of FORCE-RLS tables otherwise omit or reject tenant rows.

At startup, deploy and restore treat canonical current/pending state as authoritative. Deploy reconciles pending before previous-release discovery; restore does so before loading current identity. With pending state, reconciliation inspects the complete runtime: Postgres and Caddy must be present, control and all three core workers must use the bundle's exact raw IDs, enabled connectors must both match, and disabled connectors must both be absent. If runtime matches pending, its full health check must pass before pending is promoted. If runtime still matches current, pending is durably discarded. One compatibility recovery covers pre-activation residue from the canonical-state migration release: only when neither strict bundle matches may a complete canonical current bundle be checked against the known legacy exact-SHA `Config.Image` form, and every running application container must still have the canonical immutable Docker `.Image` ID; tags alone never establish identity. After full health and connector-presence checks, compatibility projections are atomically repaired from canonical current before the stale pending bundle is durably removed, so any projection write or unlink failure preserves the pending journal and fails closed. The same narrow canonical proof remains available with no pending journal, making that recovery retry-safe if the process stops immediately after durable pending removal: Postgres, Caddy, every required application container, connector intent, immutable IDs, exact raw-ID or canonical SHA-tag `Config.Image`, and health must all still agree. A tag-only identity or any partial, missing, wrong-ID, wrong-reference, or mixed runtime remains refused. Outside that compatibility case, disabled connector containers are removed immediately and the canonical application runtime must be either a complete healthy exact raw-ID fleet or completely stopped. With pending but no current, only an all-application-absent exact first-boot journal is retained for target-bound resume. This recovers SIGKILL after preactivation journaling, activation, current-file rename, durable compatibility recovery, or partial compatibility projection without guessing from tags.

A host with only legacy projection files can migrate only from a complete, coherent running fleet. Control and every core worker must have exact immutable identity, all three core workers must agree, validator and connector intent must validate, and health must pass. The script journals that observed bundle as pending and promotes it only after the same raw-ID and health proof. Partial, conflicting, or stopped legacy fleets fail closed. Control, core, connector, and validator identities may share a tag only when their immutable IDs also match; same-tag/different-ID records or builds are rejected wherever identities meet.

Every normal deployment and explicit or automatic rollback writes the complete intended bundle to `release-image-pending` before replacing runtime containers. Promotion occurs only after health and exact raw-ID verification. Atomic bundle and projection publication uses a private file in the state directory, mode/owner/link-count validation, file `fsync`, parent-directory `fsync`, `os.replace`, a second parent `fsync`, and proof that rename consumed the source. Durable unlink also fsyncs the parent. Promotion renames pending over current, then regenerates all four legacy projections from canonical current; projections are never read as authority once canonical state exists. A fault before rename preserves the old current bytes, and an interruption after current rename self-recovers by regenerating projections.

Before every core activation, all seven old runtime services—Caddy, control plane, three core workers, and two connector workers—go through one bounded stop → kill fallback → remove sequence, and every service must be verified container-free before the exact `compose up`. This explicit replacement does not use `--remove-orphans`.

Every Compose ops one-shot is routed through `compose_ops_run`, which assigns a deterministic exact name (`astranull-deploy-<purpose>-<pid>` or `astranull-restore-<purpose>-<pid>`), applies a bounded Compose timeout, and does not rely on `run --rm`. The isolated release-image Node validator uses the same deterministic namespace. Helper-local success, error, and timeout handling performs a separately bounded `docker rm -f`, enumerates containers, and verifies that exact name is absent. The parent deploy rollback/error trap and restore EXIT trap remove only the current operation's exact PID namespace. Separately, after the next process acquires the shared lock, startup enumerates the bounded union of prior `astranull-deploy-*` and `astranull-restore-*` one-shots, force-removes each exact validated name, and verifies no stale release one-shot remains before touching orphan files. This covers both ordinary signals and SIGKILL without selecting unrelated containers. Any removal or absence-check failure is reported as critical cleanup status `125` rather than being hidden by the original failure.

After the first HUP, INT, or TERM starts deploy rollback or restore cleanup, cleanup clears recursive EXIT/ERR traps and ignores further HUP/INT/TERM. Repeated signals therefore cannot interrupt named-container removal, private render/environment deletion, checked plaintext deletion, rollback or post-outage fail-close, release-journal verification, orphan cleanup, or snapshot cleanup. Successful deploy finalization uses the same signal-immune discipline through settled-state/projection checks and bounded image cleanup. Lock fd 9 remains held until the process exits; signal handling is never restored early enough for another deploy/restore to overlap unfinished cleanup.

Successful deploy cleanup prunes images only in the exact `astranull-control-plane:<40-lowercase-hex>` and `astranull-release-validator:<40-lowercase-hex>` namespaces. It preserves every tag referenced by canonical current, canonical pending, or a running container's exact `Config.Image`; refuses to scan more than 256 matching refs; removes only obsolete matching refs; and verifies at most **11** matching refs remain across both namespaces. It then considers only image IDs reached through those removed refs and removes an ID only if it is now dangling. It never invokes global `docker image prune` and never removes unrelated repositories or tagged images. Any enumeration, bound, removal, or verification failure is visible and fails finalization.

The exact-commit build contract remains `git archive "$SHA" | docker build ... -`; it must never fall back to the orchestration worktree. The AWS Dockerfile is referenced by the deploy helper, not by Compose. [`release-archive-inputs.txt`](release-archive-inputs.txt) indexes every `ops/aws/Dockerfile` `COPY` source plus runtime-critical leaves such as `scripts/worker-heartbeat-health.mjs` and the vendored notices. The executable unit contract inspects the real `HEAD` archive. During the current pre-commit worktree only, an intended untracked input may produce an explicit diagnostic instead of pretending it is already in `HEAD`; every such path **must be tracked in the final commit**, and a clean CI checkout fails if it is absent. This AWS boundary does not change the repository-root `docker-compose.yml`, which remains the separate local non-AWS build workflow.

The hosted test-policy scheduler accepts only 5–30 second intervals (default and maximum 30). Each successful invocation is bounded to 120 seconds, so the longest valid success-plus-sleep cycle is 150 seconds—30 seconds inside the 180-second heartbeat freshness window. The heartbeat is written only after a successful tick; failed or timed-out ticks leave it unchanged, allowing sustained failures to become unhealthy, while `restart: unless-stopped` retains process-exit restart behavior.

### Backup handoff contract for deploy/rollback automation

The shell owner must use these four boundaries in order. `pg_dump` must **not** run through `exec postgres`, as `-U astranull`, or inside the encryption service. With the deploy script's existing bounded Compose wrapper and `/opt/astranull-backups` mount, the command contract is:

```bash
# Remove interrupted private partials/plaintexts and unmatched artifact/manifest files first.
cleanup_backup_orphans
allocate_plaintext_backup # exclusive random $BACKUP_DIR/.astranull-plaintext.deploy.XXXXXX
plain_name=${plain_host##*/}

# 0. First-upgrade-safe role setup. This changes only the dump role and grants; it does
# not apply migrations or start a runtime service.
compose_ops_run 90 backup-role-bootstrap backup-role-bootstrap

# 1. Dump as the read-only backup role. The service receives only its backup DB URL.
validate_plaintext_file_security "$plain_host" 'before pg_dump' 0
compose_ops_run 180 pg-dump \
  -u "$(id -u):$(id -g)" -v "$BACKUP_DIR:/backup" backup-dump \
  sh -eu -c 'umask 077; exec pg_dump --format=custom --no-owner --no-acl \
    --dbname="$ASTRANULL_BACKUP_DATABASE_URL" --file="$1"' sh "/backup/$plain_name"
validate_plaintext_file_security "$plain_host" 'after pg_dump' 1

# 2. Before encryption, make the pinned PostgreSQL tooling parse the complete custom archive.
validate_plaintext_file_security "$plain_host" 'before structural parse' 1
compose_ops_run 60 pg-restore-list \
  -u "$(id -u):$(id -g)" -v "$BACKUP_DIR:/backup:ro" backup-dump \
  sh -eu -c 'exec pg_restore --list "$1" >/dev/null' sh "/backup/$plain_name"

# 3. Stream-encrypt that file. This service receives only the backup encryption key.
validate_plaintext_file_security "$plain_host" 'before encryption' 1
compose_ops_run 180 backup-encrypt \
  -u "$(id -u):$(id -g)" -v "$BACKUP_DIR:/backup" backup \
  node scripts/postgres-backup.mjs --input "/backup/$plain_name" --out /backup \
    --label "predeploy-${previous:0:12}" \
    --database-host postgres --database-port 5432 --database-name astranull
```

The backup directory itself must be a deploy-user-owned, non-symlink directory at mode `0700`. Plaintext is allocated exclusively with randomized `mktemp` under that directory, never at a predictable name. At allocation, immediately before and after `pg_dump`, before structural parse, before encryption, and before deletion, the host requires a regular non-symlink file at mode `0600`, owned by the deploy user, with link count exactly one (and nonempty after the dump). A link-count anomaly is a CRITICAL possible hard-link exposure: deletion of the named path does not erase the incident and cleanup returns failure. Checked deletion also verifies final absence including symlinks.

`postgres-backup.mjs` encrypts to private randomized artifact and manifest partials created exclusively at mode `0600`. It fsyncs each partial and the parent directory, durably renames the encrypted artifact first, then durably renames the manifest last. The final manifest is therefore the sole completion marker. Before returning or printing success, the writer reopens the pair, verifies regular singly linked mode-`0600` files, stable artifact inode/size/timestamps, exact encrypted size, and the encrypted SHA-256; any failure durably removes both final paths. A SIGKILL between renames can leave an encrypted artifact but cannot advertise a complete restore point. Deploy first kills and verifies stale prior-PID writers, then cleanup removes only allocator-exact scratch basenames: env and plaintext deploy/restore files with exactly six ASCII alphanumeric `mktemp` characters; build-iid files with six; previous/target Compose snapshots with six plus `.yml`; Compose render/source files with a numeric PID; and a hidden writer partial whose basename embeds an exact calendar-valid current backup name followed by `.partial-artifact-` or `.partial-manifest-` and exactly 24 lowercase hexadecimal characters. Every other file, directory, or symlink is preserved, including broad-prefix collisions and every name ending in final `.dump.enc` or `.dump.enc.manifest.json`; cleanup never turns an unknown final name into absence. Exact calendar-valid pre-nonce legacy artifacts (`postgres-YYYY-MM-DDTHH-MM-SS-mmmZ.dump.enc`) and their manifests are preserved byte-for-byte, never validated, renamed, migrated, emitted, included in retention, or pruned. Unknown final artifact/manifest names are also preserved, and any unknown `*.dump.enc` fails deploy inventory closed. An interrupted exact-current final artifact without its manifest likewise fails pair inventory and requires explicit operator disposition. Every discovered final `*.dump.enc`, including ignored legacy and unknown names, counts toward the 64-item inventory cap.

Only exact current pairs enter inventory. Inventory opens both files with `O_NOFOLLOW`, takes bigint `fstat` identities, reads the bounded manifest and streams the artifact hash only through those same handles, takes post-read `fstat`, then performs final pathname `lstat`. Artifact and manifest must each remain a singly linked regular file with unchanged device, inode, size, nanosecond mtime/ctime, mode, uid, gid, and link count. No bare or arbitrary filename enters shell retention: successful inventory emits a fixed 19-field, tab-delimited line containing the strict current name and both immutable identities. Retention validates that line shape, sorts only strict current records under `LC_ALL=C`, keeps the newest 10, then passes expired records back to the no-follow validator. It preflights every selected pair before capturing anything and reopens/rechecks each exact identity again at the retention boundary. For each unchanged pair, retention creates an exclusive mode-`0700` quarantine directory on the same filesystem inside the mode-`0700` backup root. It opens the completion manifest with `O_NOFOLLOW`, performs the last handle/path identity check, and uses a no-replace atomic rename to capture the public manifest path in quarantine. Matching handle, `fstat`, and `lstat` checks plus quarantine/root `fsync` make that public removal durable before artifact capture begins. Artifact capture repeats the same identity-bound no-replace rename, verification, and durable directory sync.

After both public paths are durably absent and one final pair-wide identity barrier succeeds, blocks are reclaimed only through the two validated held file descriptors: the helper calls identity-bound `ftruncate(0)` and `fsync` for the captured manifest and artifact. Linux provides no atomic compare-and-unlink-by-inode operation, so retention does **not** unlink either captured pathname or remove its quarantine directory. Instead it durably retains a private mode-`0700` quarantine containing two zero-byte tombstones. Tombstone directories are ignored by backup inventory and retention admits at most 4096 total; a prune that would exceed that cap fails before creating or capturing a new quarantine. Any path swap, hard-link change, size/timestamp/mode/owner drift, capture mismatch, or fsync failure aborts. A captured mismatch remains in the private quarantine for operator recovery, a source-path replacement is never unlinked, and artifact capture cannot begin before durable completion-marker removal. Operators must never rename a tombstone or its `artifact`/`manifest` members back into the public backup inventory namespace; tombstone removal, if ever required, is a separate quiesced operator procedure.

The plaintext structural listing is mandatory before encryption; a `PGDMP` prefix alone is not enough because `pg_restore --list` must parse the archive. The automation then runs `postgres-restore-drill.mjs --validate-only` against the published encrypted pair and removes plaintext before migration. `postgres-backup.mjs` refuses a production direct-dump URL unless its user is `astranull_backup`; input mode accepts no DB URL. `postgres-restore-drill.mjs` accepts only the encryption key and manifest/artifact paths. `deploy.sh` implements this exact handoff, validates both the plaintext structure and encrypted pair, and fails hosted promotion if any boundary fails.

Verify role posture after deployment without printing credentials. These checks address only `postgres`, but Compose still resolves every service image while parsing the model. Run the whole subshell: it loads `release-image-current` through the shared strict bundle parser, intentionally binds the connector variable to the canonical core ID for these postgres-only checks, never reads the four compatibility projections, never writes image IDs to `.env`, and unsets all three variables on completion or signal. For commands that actually operate connector services, use the canonical connector fields only when `connector_enabled=1`; never infer intent from `connector-image-state`.

```bash
(
set -euo pipefail
cd /opt/astranull
DEPLOY_STATE_DIR=/opt/astranull-backups/deploy-state
STATE_LOG_PREFIX=role-check
# shellcheck source=ops/aws/release-state.sh
source ops/aws/release-state.sh
release_bundle_load "$CURRENT_RELEASE_BUNDLE_FILE"

cleanup_compose_image_ids() {
  unset ASTRANULL_CONTROL_PLANE_IMAGE_ID \
    ASTRANULL_CORE_WORKER_IMAGE_ID \
    ASTRANULL_CONNECTOR_WORKER_IMAGE_ID
}
trap cleanup_compose_image_ids EXIT
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM

ASTRANULL_CONTROL_PLANE_IMAGE_ID=$release_bundle_control_image_id
ASTRANULL_CORE_WORKER_IMAGE_ID=$release_bundle_core_image_id
# Safe for postgres-only role checks: no connector workload is created or inspected.
ASTRANULL_CONNECTOR_WORKER_IMAGE_ID=$ASTRANULL_CORE_WORKER_IMAGE_ID
export ASTRANULL_CONTROL_PLANE_IMAGE_ID \
  ASTRANULL_CORE_WORKER_IMAGE_ID \
  ASTRANULL_CONNECTOR_WORKER_IMAGE_ID

docker compose -f ops/aws/docker-compose.yml --env-file ops/aws/.env exec -T postgres \
  psql -U astranull -d astranull -v ON_ERROR_STOP=1 -c \
  "SELECT rolname, rolsuper, rolcreaterole, rolcreatedb, rolinherit, rolbypassrls FROM pg_roles WHERE rolname IN ('astranull_app','astranull_backup') ORDER BY rolname;"
docker compose -f ops/aws/docker-compose.yml --env-file ops/aws/.env exec -T postgres \
  psql -U astranull -d astranull -v ON_ERROR_STOP=1 -c \
  "SELECT r.rolname, count(*) AS owned_tables FROM pg_class c JOIN pg_roles r ON r.oid=c.relowner WHERE r.rolname IN ('astranull_app','astranull_backup') AND c.relkind IN ('r','p') GROUP BY r.rolname;"
docker compose -f ops/aws/docker-compose.yml --env-file ops/aws/.env exec -T postgres \
  psql -U astranull -d astranull -v ON_ERROR_STOP=1 -c \
  "SELECT privilege_type, count(*) FROM information_schema.role_table_grants WHERE grantee='astranull_backup' GROUP BY privilege_type ORDER BY privilege_type;"

```

Expected: neither role is superuser/creator/owner; `astranull_app` has `rolbypassrls=f`; `astranull_backup` has `rolbypassrls=t`, `rolinherit=f`, and only `SELECT` table grants.

## Rollback

Every successful deploy prints the prior exact revision and encrypted backup artifact. Code rollback is explicit:

```bash
bash /opt/astranull/ops/aws/deploy.sh --rollback <prior-40-character-sha>
```

Rollback candidates must be ancestors of `origin/main`; the restored stack is health-checked. Explicit rollback resolves validator, control/core, and connector intent from canonical current state before building the selected candidate or beginning backup work. It builds the selected ancestor from `git archive` without moving the current checkout, retains the current Compose contract, validates that contract with the durable current validator, and keeps core workers plus backup one-shots on the exact durable core/ops tag+ID. The selected ancestor image runs the control plane and, only when current validated Compose enables connectors and the image proves `--queue-only` split-scheduler support, both connector workloads. Disabled intent keeps connector workloads absent. Core services always start and pass health/image verification before connectors start.

Before explicit rollback activation, the complete selected-control/current-core/current-validator/connector intent is durably written to `release-image-pending`. It is promoted to canonical current only after every required service is healthy and exact raw IDs match. Automatic rollback follows the same atomic rule but uses the validator for the Compose snapshot retained during rollback; it never assembles success from independent projection files or substitutes Git HEAD or a mutable tag. Connector-enabled retained Compose requires a compatible prior connector identity or the rollback fails closed. A state-write or promotion failure prevents rollback from reporting success. A first activation failure with no prior canonical release fails closed rather than inventing rollback state. If rollback cannot restore health/image/state, the common bounded stop → kill fallback → remove path must verify every runtime container absent and durably discard unactivated pending intent before the stopped canonical current release can be retried; a survivor is reported as an incomplete shutdown requiring immediate operator action. Database migrations are not automatically reversed. A failed deployment reports when migrations may have advanced and identifies the encrypted predeploy backup. Forward migrations retain previous-release write contracts throughout their rollback windows: migration `0044` fills target values omitted by the old writer, and migration `0045` accepts old `event_driven` policy writes only through a compatibility trigger plus CHECK that force them paused, disabled, and unscheduled. The current application contract and scheduler continue to omit that cadence.

## Governed database restore

A restore is destructive and causes an outage. Run it only with explicit incident/change approval, after recording the encrypted backup and manifest paths. Before extracting plaintext or stopping anything, the executable wrapper acquires the same lock as deployment. If pending exists, it first reconciles that journal against the complete raw-ID runtime and health, promoting or discarding it only under the rules above; mixed state fails closed. It then loads control, core/ops, validator, and connector intent from canonical current, rejects same-tag/different-ID collisions, resolves every immutable ID, and rebinds each dedicated tag. Worker and validator identity are never inferred from Git HEAD, compatibility projections, or a mutable tag. One private Compose render is validated by executing the canonical validator's raw ID, and rendered connector mode must agree with canonical connector intent. Enabled mode requires exact connector tag+ID and a successful split-scheduler compatibility probe; disabled mode requires both connector services absent. Any running control-plane, core, or enabled connector container must match its canonical identity. A legacy-only host may create canonical state only after validator, connector intent, complete runtime IDs, and health all agree.

Still before outage, the database-credential-free `backup` service authenticates and extracts plaintext exactly once to an exclusive random mode-`0600` path. The canonical validator parses the manifest's authenticated plaintext SHA-256. Before structural parsing, use, and checked deletion, the host requires a regular non-symlink file owned by the restore user with mode `0600` and link count exactly one. It hashes the complete plaintext while proving device/inode/size/mtime/ctime remain stable and requires the digest to equal the authenticated manifest; the pinned `backup-dump` PostgreSQL image must also run bounded `pg_restore --list`. A hard-link anomaly, digest change, inode replacement, or structural failure is CRITICAL. A preflight failure removes plaintext through signal-immune EXIT cleanup and leaves the runtime intentionally untouched. After the bounded stop → kill fallback → remove path verifies every runtime/ingress container absent, the wrapper repeats the full security/digest/structure check immediately before database recreation, then repeats it after recreation immediately before `pg_restore`. Restore deletes plaintext immediately after restore and before migration, starts/verifies core services first, and starts connectors only for enabled intent with compatible canonical state. There is no second extraction. After the outage boundary, any failure makes EXIT cleanup remove any remaining plaintext and use the same verified runtime-removal path; it reports immediate operator intervention instead of claiming services are stopped if any container survives.

```bash
cd /opt/astranull
bash ops/aws/restore.sh --yes \
  /opt/astranull-backups/<backup>.dump.enc.manifest.json \
  /opt/astranull-backups/<backup>.dump.enc
```

After pre-outage extraction and structural archive validation, followed by verified runtime removal, the wrapper performs both destructive operations in deterministic named `restore-db` one-shots—not through `exec -T postgres` in the long-lived database container. `restore-db-recreate` receives only the exact owner maintenance/target URLs and uses the maintenance database to terminate straggling sessions, drop `astranull`, and recreate it from `template0`. `restore-db-archive` runs as the host UID/GID with the backup directory mounted read-only and restores into the owner target URL. Destructive work has two timeout layers so an in-container process cannot outlive its Compose client: the outer bounds are 90 seconds for `psql` and 600 seconds for `pg_restore`, while the inner bounds are `timeout -k 10 75` and `timeout -k 30 540`, respectively. Parent signal/EXIT cleanup enumerates only this operation PID's deterministic names, force-removes those containers while the shared deployment lock is still held, proves absence, and leaves unrelated PID namespaces untouched. It then proves checked plaintext deletion immediately, reapplies migration head and transactional app-role grants, and waits for service health. Recreating the database is required: `pg_restore --clean` removes only objects represented in the archive and can leave post-backup objects behind as a hybrid schema. Successful completion also requires one settled canonical current bundle, no pending journal, exact runtime IDs/health, and repaired compatibility projections.

Before closing the change, independently verify `/health`, `/ready`, all worker heartbeat health states, migration head, `astranull_app` posture/zero ownership, tenant RLS smoke tests, login, and portal reads. Retain the encrypted artifact and manifest; never retain or copy the plaintext dump.
