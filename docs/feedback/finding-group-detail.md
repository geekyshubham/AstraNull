## Proposed hierarchy

Group outcome → affected/open/accepted/closed counts → asset table with own verdict, severity, owner, source run → individual finding action.

## Prioritized findings

### 1. [P1] Grouping must not create a universal verdict

**Observed / evidence:** The route groups findings across assets and can derive representative context.
**User impact:** A representative pass/severity cannot describe every member’s current state.
**Recommendation:** Show worst severity as an explicit aggregate and per-asset evidence/lifecycle; label representative explanation as an example.
**Acceptance check:** Open and accepted/closed assets remain distinguishable; no group score or pass erases member gaps.

### 2. [P2] Group route uses a different identity parameter

**Observed / evidence:** This page resolves ?key=, unlike most detail routes using ?id=. Invalid key shows an unavailable group.
**User impact:** Handoffs and stale bookmarks can produce a dead end.
**Recommendation:** Always use the canonical group link builder, preserve filter/variant on return, and show a useful unavailable-group recovery path.
**Acceptance check:** A link opened from Refined findings resolves the same group; invalid key remains an explicit empty/error state.

### 3. [P2] Rule versus asset language needs consistency

**Observed / evidence:** Screen says alert group while queue uses findings/rules and assets/targets.
**User impact:** The object model feels larger than it is.
**Recommendation:** Choose Finding group and Affected targets; explain one issue across multiple endpoints without changing API identity.
**Acceptance check:** List/detail/report/notification refer to the same group and count definitions.

## Actions, dialogs, widgets and states

Inspect real canonical grouped link, lifecycle asset filters, search if offered, member finding links and return to queue. Invalid-key state was exercised before resolving a real canonical key; that is not a product defect. No bulk close/accept is implied without explicit backend semantics.

Keep loading, retained/stale data, unavailable, no data, filtered-empty, disabled-by-role, invalid input, saving, error and success states distinct. Use the shared dialog/keyboard/focus contract; destructive confirmations state the exact affected object.

## Data and functionality prerequisites

Use canonical key generated by finding-groups.mjs; target identity and each member’s source evidence are preserved. Tags/groups are context, not grouping evidence.
