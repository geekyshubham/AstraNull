# ADR-0023: Durable reviewed inert-operation preflight

Date: 2026-10-10

Status: Accepted for preflight persistence only; execution integration is not delivered.

## Context

Mechanism-specific request delivery must not turn a small payload or a customer declaration into permission to perform arbitrary application operations. Existing outside-in checks cannot safely add generic POST bodies, callbacks, custom headers or ambiguous framing merely because their traffic budgets are small. Exact endpoint semantics, current ownership, safe serializers and independent controls are separate requirements.

The user excludes new customer cloud/read-only integrations and new SOC/governed workflows. This change adds an authenticated customer preflight record to existing declared targets, not a new SOC workflow, customer agent or environment. Existing high-scale gates are unchanged.

## Decision

Store versioned `reviewed-inert-operation.v1` records for one directly owned, active declared URL and one current safe catalog check. Preview is passive and requires `test_run:read`. Approval and revocation require `test_run:start`, an authenticated human owner/admin, and any applicable token scope. A service account cannot approve or revoke, even when its role and scope would otherwise permit a test start.

The plan pins the exact canonical endpoint, target definition digest, catalog check version and credential-stable catalog definition digest, scenario, fixed template/method/schema/limits, declared inert semantics and expiry. Only `marker-query-v1` and `inert-json-v1` are accepted; the latter is limited to evasion-marker definitions. Credentials, existing query strings, fragments, non-HTTP endpoints and a conflicting declared port are rejected. Expiry must be a valid UTC ISO timestamp and at most 24 hours after approval. Request-provided actors, approvals, endpoints, headers, raw bodies and callbacks are rejected, not ignored.

The client previews the full plan and sends its `reviewed_plan_digest` with unchanged input. The server reconstructs the plan using current target and catalog state before writing. Approval actor, role and timestamp are server-derived. Same-tenant digest replay returns the original row without another approval audit. Revocation is terminal. Read projections reconstruct typed plans and disclose expiry, target/check drift or lost ownership without rewriting historical plans.

Migration `0075_reviewed_inert_operations.sql` adds `reviewed_operations`, same-tenant target foreign key, unique tenant/digest identity, constrained plan JSON, FORCE RLS and immutable-history trigger. PostgreSQL locks the target and existing direct verification rows through review and transactional audit. Same-target approvals/revocations serialize with an advisory transaction lock. Reads re-fetch the current record inside that lock rather than returning an optimistic pre-lock revocation state. Auditing failure rolls back the PostgreSQL mutation. Review transactions acquire the canonical tenant audit advisory lock before review/target/verification locks, matching catalog mutation order. An actual two-client PostgreSQL regression reproduced the previous audit↔target deadlock (`40P01`) and verifies that an audit-lock holder can update the target while approval waits without holding a conflicting target lock.

## Explicit execution boundary

Every successful preflight/review result has `grants_execution: false` and `execution_available: false`; errors never grant execution. No review creates a run, job, reservation, baseline or destination request. Inert semantics are customer declarations, not proof that the application is side-effect-free. Preview and persisted approval do not establish WAF enforcement, origin lockdown, CVE mitigation or DDoS readiness.

No worker transport or dispatch limit is relaxed. Before any future delivery is enabled, the lifecycle must bind the reviewed immutable plan into signed job authority, revalidate current target/ownership/expiry/revocation at admission and reservation, and obtain fresh independent same-envelope controls. Existing per-check allowances, one-shot reservations, kill switch and authorization deadlines remain mandatory. Locking existing verification rows is not a claim that all future ownership state writers or execution races are already integrated.

The pure `reviewed-operation-binding.v1` foundation additionally reconstructs strict current review/material definitions, human approval identity/time, direct DNS ownership, the original two-minute deadline capped by review expiry, exact destination/profile and separate resolver/probe budgets. It enumerates only the already supported GET query-evasion shapes; cookie/path/header/body/HEAD variants, `inert-json-v1` and other delivery remain unavailable. Pure tests do not create a run, job, grant or request. This module is not wired into admission, recovery, reservation or the worker yet. The concrete profile is losslessly hashed and exact reconstruction rejects post-binding profile drift. The human review's catalog digest intentionally does not pin every credential-like profile metadata value; current supported serialization uses enumerated transforms and fixed marker-class constants, not arbitrary marker text. A future serializer consuming such text must add lossless approval authority/versioning before it is enabled.

Original jobs are signed before worker leasing/reservation; attaching a later reservation to their signed constraints would mutate immutable authority. The structural reservation guard therefore compares a separately supplied future signed-grant reservation to the original job/review/deadline/budgets and exact authenticated worker/lease. Grant signature verification is an explicit prerequisite, not a boolean shortcut. Independent grant signing/verification and runtime integration are not implemented by this pure foundation, so it grants no execution.

## Exact URL ownership and fail-closed runtime prerequisite

Reviewed consumers require the declared URL's own current direct DNS row with server-issued `dns-ownership-target.v2` identity and material definition digest in `source_ref.dns_target_binding`. Retained unbound URL rows, sibling FQDNs, inherited/provider/manual/demo proof cannot approve a new material URL plan. URL/path/port/protocol/expectation/declaration drift requires new exact proof before another review. This is stricter than retained ordinary target compatibility and does not rewrite historical rows. Explicit URL issuance derives only a host TXT name, never endpoint I/O. Its exact typed material binding survives failed checks, expiry and successful terminal replay; compatibility issuance/verification without explicit selection remain FQDN-only. Complete scoped provenance hashing and exact private PostgreSQL challenge microseconds prevent stale asynchronous lookup completion. Public challenge timestamp presentation and existing intake normalization remain unchanged.

Until the dual-signature and current-authority lifecycle is complete, run admission explicitly rejects selected `reviewed_operation_id` (`reviewed_operation_execution_unavailable`) before locking, replay or mutation. Malformed/caller-supplied review authority is rejected, never silently discarded. Worker direct/signed entry also denies reviewed jobs before DNS/socket/HTTP. Polling denies before requesting the ordinary unsigned `/execute` reservation. Dev/PostgreSQL ordinary reservation and accepted-result ingestion deny reviewed jobs, and the repository's SQL predicate independently checks stored reviewed constraints against a stale caller descriptor. Stop acknowledgments remain available. These guards do not implement execution; adding a typed grant library alone must not remove them.

Material authority uses `assurance-scope.v3` and `dns-ownership-target.v2`. Catalog credential-version redaction is not authority hashing: URL/declaration/policy values containing credential-like text remain losslessly bound, and canonical JSON preserves own literal `__proto__` keys at every nesting level. Ordinary canonical bytes are unchanged by the own-key repair. Older scope/DNS versions remain historical and fail closed for current authority; no backfill, custody rewrite or legacy permissive fallback is added.

After asynchronous lookup, PostgreSQL now checks supplied challenge/target snapshot material **before** replaying terminal success. An unchanged competing completion may advance history generation and retain its original audit without new proof; changed URL/token/binding/private clock material returns `challenge_binding_changed` without success writes. Natural expiry after already-completed unchanged success does not rewrite that historical result.

## Independent grant foundation

The detached `reviewed-execution-grant.v1` library signs a full purpose-separated Ed25519 envelope (`astranull.reviewed-operation.execution-grant`), not a custody digest or worker HMAC. The envelope binds the byte-identical original canonical eight-field job payload, SHA-256 of its unchanged original signature string, tenant/job/run/check/target/nonce, authenticated worker/lease, complete `reserved_unknown` reservation, separate budgets and unchanged original deadlines. Top-level `target_id` must equal the HMAC-signed descriptor id. A later reservation never enters original signed constraints.

Verification uses dedicated public-only pinned trust and the shared strict Ed25519 point importer. Current verification requires an active key and unexpired original authority. Historical verification may use a retained retired public key and explicitly returns `execution_valid: false`; it is not renewed permission. Typed shape, JSON, clocks, purpose, algorithm, fingerprint and exact reconstruction are mandatory. No caller boolean or metadata can replace either signature.

Purpose-specific local and bounded HTTPS adapters exist. The external adapter sends the complete envelope to `/v1/reviewed-execution-grants/sign`, verifies the actual returned signature, and bounds signer/body wait, cancellation and late response cleanup. Dedicated grant environment names cannot fall back to custody configuration. These are detached adapters, not a new public API or enabled deployment.

This foundation does **not** authenticate the original HMAC, establish current database/review/revocation/DNS authority, durably issue/consume a unique grant, or enforce uniqueness across signing calls. Runtime must supply those independently and revalidate after signing. Startup configuration, persistent issuance, uncertain signer outcomes, recovery, reservation/result custody and worker integration remain unfinished. Mock signer tests are not real signer availability, key rotation or operational acceptance. All existing fail-closed reviewed runtime guards remain mandatory.

## Internal current-authority prerequisite

`createReviewedOperationAuthority({ backend }).withCurrentAuthority(ctx, request, callback, options)` now supplies an internal current-row prerequisite, not an HTTP endpoint or execution permission. Build requests contain exactly `mode: 'build'`, `reviewId`, `targetId`, `checkId` and `originalAuthority: { issued_at, not_after }`. Compare requests contain exactly `mode: 'compare'`, `targetId`, `checkId` and the stored `binding`; review identity and unchanged original authority come from that binding. Original/compare authority labels require canonical UTC three-digit milliseconds. Caller records, selectors, replacement deadlines, accessors and non-JSON bindings are rejected; no historical label is upgraded.

PostgreSQL acquires the canonical tenant audit advisory lock, then the reviewed-target advisory lock, active group/full target/all direct ownership history/review row locks. It reads full ownership chronology with exact microseconds before lossless `.ddd000Z` normalization; genuine sub-millisecond, malformed, ambiguous or obsolete authority cannot fall back to an older proof. Fresh `clock_timestamp()` is sampled after lock waits. Validation and the consumer callback execute before the same managed tenant transaction releases its locks. Explicit clients must be the exact active same-pool/same-tenant managed client: pools, autocommit and untracked manual transactions are rejected. A caught nested callback failure still poisons the enclosing transaction.

Successful snapshots are detached and deeply frozen; finite driver Dates become immutable ISO strings while exact authority strings retain their precision. Snapshot results retain `grants_execution: false` and `execution_available: false`. Dev loading supports synchronous actual-row consumers only and does not claim to lock catalog/ownership writers or make asynchronous signing safe. Runtime reuses the existing review backend for the loader, without registering an execution route.

Final focused tests pass **78/78** (56 authority units, five managed-client units, 17 actual PostgreSQL application-role cases); affected compatibility tests pass **521/521**, both with zero skips. This does not authenticate original job HMACs, validate grants, establish leases/reservations/kill switches/admission, or durably consume issuance. Signing must not occur inside a rollbackable authority callback: a future issuance orchestrator needs a confirmed durable claim commit and fresh post-signing revalidation. Reviewed runtime deny guards remain unchanged.

## Consequences

Historical checks and custody are unchanged; no review or proof is backfilled. PostgreSQL startup requires the additive migration through the normal operator migration process. Missing or partially wired PostgreSQL services fail closed with `postgres_route_not_wired`, without dev-store fallback. No production migration or deployment is performed by implementing or locally testing this feature.

The customer-facing execution workflow, signed admission/reservation binding, actual independent baseline producers, mechanism-specific serializers and CVE-specific validation remain separate unfinished work. The progress ledger must not mark those complete from the existence of this preflight API.
