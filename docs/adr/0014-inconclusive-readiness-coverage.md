# ADR-0014: Distinguish observations from readiness coverage

Status: Accepted, 2026-10-04.

The live routelens.app snapshot had 149 latest checks, 107 inconclusive verdicts (105 in the applicable coverage plan). Thirty-five checks use transport-only executors that always produce inconclusive readiness verdicts. Forty evasion comparisons recorded an allowed baseline marker. Several other probes timed out or lacked endpoint details. Treating all these results alike hid the action needed and depressed the conclusive-coverage denominator with checks incapable of producing a readiness conclusion.

Exclude E2/observation-only executors from the readiness coverage denominator and from the portal's reviewed Run all selection. Keep individual observations and historical verdicts available. Do not relabel transport observations or timeouts as protection. Return an additive count and grouped reasons on the target detail coverage payload. Evasion/inspection comparisons without a blocked baseline remain inconclusive; explanations distinguish a missing comparison from a probe that sent no requests. Dev and PostgreSQL correlation read the recorded signed probe metadata. Existing verdicts are immutable.

The DNSSEC executor previously called Node `dns.resolve` with unsupported `DNSKEY` and `DS` types, causing `ERR_INVALID_ARG_VALUE`; these types are absent from the supported [`dns.resolve` record types](https://nodejs.org/download/release/v26.8.2/docs/api/dns.html#dnspromisesresolvehostname-rrtype). Version 2 uses one bounded DNSKEY wire query to the zone's declared authoritative nameserver path, reusing the existing destination classification and pinned DNS transport. Its signed destination budget is one NS lookup plus one A/AAAA classification pair, matching the existing DNS wire executor. It retains the existing probe cap and sends one request. A complete, matching, authoritative, untruncated successful response is required; matching DNSKEY records must contain protocol 3 and a public-key field. Key presence is not delegation-chain validation or flood resilience. `ds_count` is null and `dnssec_chain_validated` is false. Invalid/refused/non-authoritative replies and deadlines remain inconclusive. Recursion checks accept declared resolver IP targets; a website FQDN does not stand in for a resolver endpoint.

No schema migration or historical verdict rewrite is needed. Existing verdict publication and finding audit events still cover new results. Existing ownership, lease, request accounting, deadline, and SOC gates apply unchanged.

Replaying the signed live snapshot through the corrected read model yields 111 applicable pairs, 42 conclusive, 68 inconclusive (41 comparisons, 26 timeouts, one incomplete probe), one version-mismatched DNSSEC pair, and 35 excluded observations. Coverage is 38%. The DNSSEC pair requires an explicit new governed run; old evidence is not upgraded. The full-catalog FQDN evidence generator now expects 193 unique checks because open recursion is reserved for resolver IP targets; its 721 vector rows and disposition totals are unchanged.
