# ADR-0021: Bounded execution and evidence-based assurance

- Status: accepted for the current engineering remediation; not production release acceptance
- Date: 2026-10-09
- Related: ADR-0008, ADR-0013, ADR-0014, ADR-0018, ADR-0019
- Tracking: [verified capability audit remediation](../implementation/verified-capability-audit-remediation.md)

## Context

The verified capability audit identified false protection conclusions, misleading scores, incomplete live activity, and retry/admission accounting gaps. Source definitions, fingerprints, status codes, telemetry, governance and configuration are not independent proof of protection. Customer selection remains direct declared targets/domain sets; existing internal policy associations remain safety/history records, not customer group workflows.

## Decision

1. **One-shot authority.** `probe-authority-v2` signs original `issued_at`, absolute `not_after`, and `execution_attempts: 1`. The maximum lifetime is 120 seconds, shortened by the original collection and approved window deadlines. Reclaim never renews it. Worker request `pw2` authentication also binds the worker identity, method, full path, timestamp, tenant and raw body.
2. **Durable reservation before I/O.** An exact leased job obtains one `execution-reservation.v1`, conservatively reserving the entire signed operation allowance as `reserved_unknown`. Current ownership, target kind/value/port/protocol, active scope and kill switch are rechecked transactionally. Lost or ambiguous grants do not authorize retries; unknown/unspent reservations are not refunded. Reservation counts are planned maxima, never measured traffic. Positive results must match persisted worker/reservation/original-lease lineage. Zero-I/O error/not-run diagnostics and historical durable reconciliation do not authorize traffic.
3. **Complete admission.** Hourly accounting/cooldowns use complete tenant-scoped internal queries under the admission transaction, not presentation feeds; the counts feed the bypass audit flags because the policy is advisory. Missing or malformed complete usage fails closed with audited 503. Nested same-tenant repository calls share the transaction; a caught nested failure still poisons the outer transaction. Cross-tenant transaction reuse is rejected. Audit locks precede mutation locks.
4. **Truthful live inspection.** Accepted Play retains the exact returned run/scan ID and opens its Inspector. Passive cursor reads retain recorded events across reconnect and fetch the final page. `probe-capture.v1` exposes dropped/failed/bounded metadata; even complete capture means recorded metadata only, not packet capture. Reporter partition/hung sends abort execution after bounded grace. Stop requested, authenticated worker acknowledgement, unreachable and deadline elapsed remain distinct. Pausing display is not pausing traffic.
5. **Scenario-limited assurance.** Marker assurance requires current complete `marker-comparison-v4` proof, an independently healthy permitted baseline and all comparable scoped marker legs. Statuses, auth walls, fingerprints, incomplete or contradictory legs and transport silence provide no protection credit. HTTP/2 SETTINGS, DNSKEY presence, standalone origin reachability and exposure samples remain observations. Unsupported delivery/mechanisms are not runnable and never inherit a different grouped check's support.
6. **Versioned readiness.** Dev and PostgreSQL use the same pure `readiness-assessment.v2` projection and `protection-profile.coverage.v2` policy. Coverage is keyed by active applicable target/check pair; its current compatible observed proof expires after seven days. Score is floor(100 × current passing applicable pairs / applicable pairs), less bounded unresolved severity penalties: critical 20, high 10, medium 5, low 1, informational/info 0, unknown 5. Governance earns no protection credit. Unknown is neither protected nor automatically vulnerable. Incomplete inputs yield `score: null` and `input_complete: false`. Exact weighted blank-target and aggregate finding projections may reduce database/CPU cost only with complete raw/aggregate parity; no feed caps or cross-request stale cache.
7. **Immutable history and current scope.** Observation time and availability at the cutoff determine age/history; metadata updates cannot refresh old proof. `assurance-scope.v3` losslessly binds material target kind/value/port/protocol/declarations, policy association/definition and retained group material; stored v1/v2 scopes require retest. Authority hashing is separate from catalog credential-version redaction and preserves literal JSON keys. Current scope/version changes withdraw current credit and require reviewed retest without rewriting verdicts/custody. A missing past snapshot is unknown, never today's posture backfilled into the past. Comparison reports separately label their 30-day evidence freshness; this does not renew seven-day readiness. Current positive credit requires same-tenant exact-run signed proof with matching correlation nonce, immutable ingestion availability and a compatible actual performed outcome; a retained positive string cannot override contradictory enforcement. Reports resolve recorded current group/policy definitions and rederive scenario/expectation classification from actual observations, not references alone. Unattributed edge denial does not independently prove both WAF and CDN or inner-layer enforcement.
8. **CVE/remediation honesty.** Validated mitigation requires approved component/version/scenario applicability, exact mitigation binding and retest lineage. There is currently no approved generic catalog mapping for a specific safe CVE executor. Administrative disposition/task completion remains distinct from validated mitigation; fingerprint-only or inconclusive retests cannot close it.
9. **Existing notification atomicity.** PostgreSQL high/critical protection finding creation or meaningful escalation enqueues the existing subscription/deduplicated outbox in the finding transaction with deferred recovery delivery. Rollback cannot leave a committed domain/outbox split. No outbound send occurs before commit. This adds no channel, integration or live provider certification.

## DNS ownership finalization hardening (2026-10-10)

A TXT lookup result is not permission to overwrite intervening lifecycle or ownership changes. Dev finalization re-fetches current challenge/target scope after lookup and compares the captured same-target ownership history; a duplicate terminal completion retains its original audit reference without another proof/audit. Pending malformed clocks and a mismatched declared hostname/kind fail before DNS.

PostgreSQL obtains a server-only `dns-ownership-check.v1` snapshot under canonical tenant-audit locking and releases the transaction before external lookup. Finalization locks the exact challenge/active scope and rechecks its immutable identity/endpoint plus a SHA-256 over complete same-target verification rows; no capped current-state feed substitutes for generation. A fresh database clock after snapshot lock waits prevents starting an already-expired lookup. Missing internal binding, scope drift or intervening ownership fails closed without success mutation. Successful challenge/verification/audits retain their existing shared transaction and duplicate completion remains idempotent. The scalar active-target lookup also uses a scalar SQL parameter, not a PostgreSQL array literal.

The DNS finalization slice introduces no migration, synthetic proof, new withdrawal/revocation endpoint, or public target traffic. Supported intervening states are existing `pending`, `unverified`, and `user_confirmed`. Local deferred-resolver and actual two-client PostgreSQL cases do not certify hosted DNS ownership or production acceptance.

## Ownership chronology hardening (2026-10-10)

Ownership strength and random row identity cannot establish chronology when legacy transitions share an instant. Dev and PostgreSQL compare complete same-tenant, same-target history using exact instants, retaining sub-millisecond precision before JavaScript date normalization. Equivalent latest state/source-kind/source-reference duplicates may retain authority. Conflicting latest authority, or any malformed/nonfinite/unrepresentable clock in the scoped history, projects the existing `pending` state with internal `source_kind: ownership_ambiguous` and empty `source_ref`. History remains immutable. Inheritance, demo compatibility and old verified challenges must not upgrade this projection; it is not a new revocation state or endpoint.

New transitions serialize and advance in whole milliseconds strictly beyond the complete scoped history maximum. Advancing only by a PostgreSQL microsecond is insufficient for millisecond execution bindings. The dev allocator validates chronology before success audits/mutations and rejects impossible advancement with `ownership_transition_invalid` (409). Additive migration `0077_ownership_transition_order.sql` provides a tenant-audit-first insert trigger, active target row lock, finite JavaScript-representable clock checks, successor-overflow rejection and a tenant-invoker current view. SQL rejection rolls back proof and linked audits. Existing legacy rows are never rewritten; the migration may withdraw ambiguous current authority without manufacturing a new proof.

Logical advancement orders proof only. DNS challenge expiry, LOA expiry, approval age and execution deadlines continue to use fresh wall clocks; they are not renewed by a later transition timestamp. Actual local app-role upgrade/concurrency and negative-control tests plus schema mutation checks exercise these contracts. Normal authorized operator migration is required before rollout; no production migration, backfill or deployment was performed.

## Lossless material scope repair (2026-10-10)

Material scope now uses lossless canonical JSON hashing rather than the catalog definition helper, whose credential redaction intentionally keeps catalog credential rotation from changing definition versions. Credential-like URL text and material declaration/policy/group keys must remain authority inputs. The shared canonicalizer preserves literal own JSON keys using a prototype-free accumulator; `__proto__` cannot disappear from a digest. Nonproblematic canonical bytes remain unchanged. Version `assurance-scope.v3` and exact URL binding `dns-ownership-target.v2` withdraw current authority from older versions without rewriting or silently upgrading immutable history. Existing retest paths remain required.

The PostgreSQL finalizer also validates captured exact material before returning a competing terminal success. History generation may differ because the first completion appended its expected proof, but URL/token/binding/exact-clock drift cannot report `verified: true`. This repair changes neither execution permission nor original expiry.

## Consequences and rollout

- Semantic check/classifier versions change; historical proof remains readable with explicit version/retest labels. Deploy control plane and workers as a coordinated compatible release. Legacy outstanding authorization is rejected for fresh execution, never accepted through an unsigned fallback; drain/recreate through existing reviewed start paths.
- Reservation/capture/Stop metadata use existing JSON persistence. The later ownership chronology slice adds migration 0077; existing PV migrations remain prerequisites where already applicable. No production migration has been applied by this work.
- Lower scores and more inconclusive/unsupported rows are intentional when prior credit lacked proof. Catalog definitions, profiles, vector mappings and independently exercised mechanisms are reported separately.
- No new cloud/read-only integration, agent, environment, discovery requirement, SOC workflow, reusable attack recipe or unmanaged traffic generator is introduced. Existing SOC gates remain mandatory.
- Local fixtures, tests and metadata validators are engineering verification, not hosted worker-stop, provider/KMS/identity/custody, human UX or production release acceptance. Those remain separately open; no deployment is authorized by this ADR.
